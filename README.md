# 우연한 식탁

처음 만나는 4~6명을 한 테이블로 묶어 주는 소셜다이닝 서비스의 MVP입니다.
신청 → 자동 매칭 → 식당·단체방·안내 → 참석·후기 → 다음 매칭 반영까지 **운영자가 손대지 않아도 흘러가고**, 운영자는 자동으로 풀리지 않은 예외만 처리합니다.

Blaybus × 와썹하우스 「우연한 식탁 MVP 개발 해커톤」 출품작입니다.

- 참가자 앱: 모바일 웹(약 420px) `/app`
- 운영자 웹: `/admin`
- 테스트 계정은 제출할 때 따로 전달합니다

## 완료 조건 12단계와 구현 위치

PRD 18절의 완료 조건을 한 데모에서 끊김 없이 보여 주는 것을 목표로 했습니다.

| # | 완료 조건 | 구현 |
|---|---|---|
| 1 | 날짜·지역을 고르고 신청 | 개인정보·운영 정책 동의, 날짜·지역 복수 선택, 이용권(1회권·멤버십) 선택, 모의 결제 |
| 2 | 마감 시각에 결제 완료자 대상 자동 매칭 | 마감 스케줄러(회차별 1회, 멱등) + 데모용 "지금 마감 실행" |
| 3 | 필수 조건·우선순위로 4~6인 테이블 | 매칭 엔진: 필수 조건 + 선호 점수(0~100) |
| 4 | 4명 미만·조건 미충족 조합 해제 후 재배치 | 재배치·분리·최소 점수 미달 해제 단계 |
| 5 | 운영자 승인 없이 자동 확정 | 확정 직전 필수 조건 재검사 후 저장 |
| 6 | 식당 자동 배정 + 단체방 자동 생성 | 확정 이벤트 → 식당 배정(예산·남은 자리 순, 실패 시 재탐색) → 단체방 |
| 7 | 단체방에서 결과·식당·큐레이션·안내 확인 | 시스템 공지 6종(환영·시간장소·큐레이션·정책·리마인드·대화 주제) |
| 8 | 미매칭 참가자 일정 추천, 이동·환불 자동 처리 | 대체 회차와 지역별 대기 인원 추천, 일정 이동·이용권 보관·자동 환불 |
| 9 | 리마인드와 대화 콘텐츠 자동 게시 | 전날 12시 리마인드, 시작 시각에 테이블 맞춤 주제·아이스브레이킹 |
| 10 | 체크인·만족도·사람별 선호 입력 | 앱 체크인, 행사 시작 4시간 뒤 자동 종료(미체크인 → 노쇼 후보), 후기·비공개 선호 |
| 11 | 다음 매칭에 이전 만남·피드백 반영 | 차단·신고·"다음엔 따로" → 같은 테이블 금지, 이전 만남 → 점수 반영 |
| 12 | 미해결 예외만 운영자 화면에 | 예외 처리함: 신고·식당 배정 실패·환불 실패·알림 발송 실패·노쇼 후보 |

## 매칭 알고리즘

엔진은 Spring에 의존하지 않는 순수 Java(`domain/matching/domain/service/MatchingEngine`)이고, 같은 입력이면 항상 같은 결과가 나옵니다(무작위 없음, 동점은 id 순).

### 필수 조건 (하나라도 어기면 테이블이 될 수 없음)
- 같은 날짜, 본인이 고른 지역
- 4~6명
- 최고·최저 나이 차 8살 이하
- 차단·신고·"다음엔 따로" 관계가 없음

확정 직전에 모든 테이블을 다시 검사하고, 위반이 있으면 저장 자체를 막습니다.

### 선호 점수 (0~100, 50점 이상만 자동 확정)

| 항목 | 배점 | 계산 |
|---|---|---|
| 성비 | 30 | 소수 성별 비율 r(절반이면 1)에 대해 `1-(1-r)²`. 한 성별만이면 0점 → 남성을 여러 테이블에 고르게 나눔 (데이터가 여 199 : 남 95) |
| MBTI 궁합 | 25 | 쌍마다 N/S 같으면 0.5, E/I·T/F가 다르면 각 0.25 (대화 결은 맞고 성향은 보완). 모르면 0.5 |
| 공통 관심사 | 20 | 쌍마다 2개 이상 겹치면 만점, 1개면 절반 |
| 희망 상대 성향 | 15 | 내가 원한 성향 중 상대가 가진 비율, 양쪽 평균 |
| 새로운 사람 | 10 | 전에 같은 테이블에 앉은 적이 없으면 만점 |

가중치·최소 점수·인원·나이 차는 `MatchingPolicy` 한 곳에 모아 두었습니다.

### 한 회차를 테이블로 나누는 순서
1. **그리디**: 인원이 적은 지역부터, 나이순으로 정렬해 가장 어린 사람을 씨앗으로 두고 나이 차 8 안에서 점수가 가장 오르는 사람을 한 명씩 추가
2. **재배치**: 남은 사람을 빈자리가 있는 테이블에 넣음 (본인이 고른 다른 지역도 후보)
3. **개선**: 테이블 사이 한 명 이동·두 명 교환 중 총점이 가장 오르는 것을 반복
4. **분리**: 남은 사람끼리 5·6인 테이블에서 멤버를 빌려 새 테이블 (예: 6+2 → 4+4)
5. **최소 점수 미달 해제**: 50점 미만 테이블을 풀어 다시 2~4단계
6. **결과**: 테이블마다 인원·나이 범위·성비·MBTI 구성·공통 관심사·점수 항목별 내역·좌석별 배치 사유를 저장하고, 못 들어간 사람에게는 사유를 붙임

못 들어간 사람은 본인이 고른 **다음 날짜 회차로 자동 이월**되고, 마지막 날짜까지 실패하면 대체 일정 이동·이용권 보관·환불 중에서 고르게 합니다.

### 벤치마크 (주최 측 가상데이터)

294명 중 서울 4개 지역을 고른 291명을 엑셀의 24개 회차에 날짜순으로 처리한 결과입니다. (`MatchingBenchmarkTest`, 결과 파일 `build/reports/matching-benchmark.txt`)

| | 그리디만 | 그리디 + 개선·분리 |
|---|---|---|
| 배정 | 208명 (71.5%) | **221명 (75.9%)** |
| 테이블 | 43개 | 48개 (4명 26 · 5명 15 · 6명 7) |
| 점수 평균 / 최저 | 69.4 / 55.7 | 69.9 / 54.4 |
| 실행 시간 (24회차 전체, 5회 중앙값) | 36.0ms | 17.8ms |
| 필수 조건 위반 | 0 | 0 |

남은 70명 중 25명은 그 날짜·지역 신청자가 4명 미만(11명)이거나 나이 차를 맞출 상대가 없어(14명) 원래 테이블을 만들 수 없는 경우입니다.

## 자동으로 이어지는 흐름

```
신청 마감(행사 전날 0시)
  └─ 자동 매칭 ─┬─ 확정 테이블 → 식당 배정 → 단체방 생성·공지 → 확정 알림 → 참석 예정 생성
               ├─ 다음 날짜로 이월 → 그 회차 마감 때 다시 매칭
               └─ 마지막 날짜 실패 → 실패 알림 → 참가자가 일정 이동·보관·환불 선택 (자동 처리)
행사 전날 12시   → 리마인드 (단체방·알림)
행사 시작        → 테이블 맞춤 대화 주제·아이스브레이킹 게시
행사 시작 + 4시간 → 자동 종료: 미체크인 → 노쇼 후보, 후기 요청
후기·신고·차단   → 다음 매칭의 필수 조건·점수에 반영
모임 다음 날      → 후기를 안 쓴 참석자에게 한 번 리마인드
새 회차 열림      → 참석 이력이 있는 사람에게 선호 지역과 함께 추천 알림
```

자동으로 풀지 못한 것만 운영자 예외 처리함에 올라갑니다. 식당은 같은 지역의 다른 식당까지 모두 실패했을 때, 알림은 1분·5분 뒤 재시도까지 실패했을 때, 환불은 결제사 환불이 실패했을 때입니다. 운영자는 거기서 다시 배정·다시 보내기·다시 환불을 누릅니다.

## 운영 정책 (PRD에 없거나 주최 측 Q&A로 정한 것)

- **신청 마감 = 자동 매칭 = 환불 불가 시점**: 행사 전날 0시(목요일 모임이면 화요일 24:00). 환불이 막히기 직전까지 신청을 받고, 마감하자마자 결과를 알림
- **이용권**: 1회권 9,900원, 멤버십 1·3·6개월 35,000·75,000·120,000원(기간 안 무제한). 멤버십은 매칭 실패 1회당 7일 연장
- **확정 후 취소**: 환불 없음. 노쇼 2회, 또는 노쇼 + 제한 시점 이후 취소 3회면 30일 자동 참가 제한
- **신고**: 상대에게 알리지 않음. 행사 전·중 신고는 긴급으로 표시해 예외 처리함 맨 위에. 신고하면 기본으로 차단(다음 매칭부터 같은 테이블 금지)
- **확정 후 인원이 3명이 되는 경우**: 필수 조건을 완화하지 않고, 일정 이동·환불은 참가자가 선택
- **단체방**: 외부 메신저가 아닌 서비스 안 채팅. 서로 별칭(참가자 N)·나이대·MBTI·관심사·성향만 보임
- **결제·환불·푸시·식당 예약**: 모두 포트(인터페이스) 뒤 모의 구현. 실제 PG·푸시·예약 연동 시 구현만 교체
- **개인정보**: 신청 전에 개인정보 수집·이용과 운영 정책 동의를 받고, 동의한 버전과 시각을 저장(정책이 바뀌면 다시 동의). 식당에는 예약명만 전달. 탈퇴하면 바로 삭제하되 결제·환불 기록은 전자상거래법에 따라 5년, 안전 신고·이용 제한 기록은 1년 보관 후 삭제

## 기술 구성

| 구분 | 사용 |
|---|---|
| 백엔드 | Java 21, Spring Boot 3.5.3, Spring Data JPA, MySQL 8.4, Apache POI(엑셀 적재) |
| 프론트엔드 | React 18.3.1, TypeScript 5.6.2, Vite 5.4.8, React Router 6.26.2 (참가자 앱과 운영자 웹을 한 앱으로) |
| 테스트 | JUnit 5, Testcontainers(MySQL 8.4) — H2를 쓰지 않고 실제 MySQL로 통합 테스트 |
| 인증 | 서명 토큰(서버 세션 없음), `/api/app/**` 로그인, `/api/admin/**` 운영자 |

### 패키지 구조

```
com.wooyeon.table
├── domain/<도메인>/
│   ├── presentation    컨트롤러·요청·응답
│   ├── application     서비스·DTO·스케줄러·이벤트 리스너
│   ├── domain          모델·도메인 서비스·저장소 포트
│   └── infrastructure  JPA 저장소 구현
└── global              설정·인증·공통 응답·예외
```

도메인: `user` `profile` `event`(회차) `application`(신청) `payment` `matching` `resolution`(실패 해결) `venue` `chat` `notification` `feedback`(참석·후기·이력) `safety`(신고·차단·제재) `operation`(운영 조회) `demo`(시연 데이터)

- 다른 도메인 데이터는 그 도메인의 QueryService로만 읽습니다.
- 신청·결제·매칭·참석 상태는 PRD 12절대로 각각 다른 enum입니다. 참가자 화면의 "상태 하나"는 이 셋에서 계산합니다.
- 매칭 확정 뒤 흐름은 Spring 이벤트로 이어집니다(식당 → 단체방 → 참석 순서 고정).
- 같은 요청이 두 번 와도 한 번만 처리되도록 DB 유일 제약으로 막습니다(매칭 실행, 결제, 실패 해결 선택, 후기 등).

## 로컬 실행

필요한 것: JDK 21, Node 18 이상, Docker

```bash
# 1) MySQL (3307 포트)
docker compose up -d

# 2) 백엔드 (8080) — 데모 데이터와 함께
DEMO_SEED_ENABLED=true DEMO_APPLICANTS_FILE=data/applicants.xlsx ./gradlew bootRun

# 3) 프론트엔드 (5173, /api는 8080으로 프록시)
cd frontend && npm install && npm run dev
```

- 참가자 앱 http://localhost:5173/app/login · 운영자 http://localhost:5173/admin/login
- 데모 시드는 **빈 DB에서 한 번만** 들어갑니다. 처음부터 다시 하려면 DB를 비우고 띄웁니다.
- 가상데이터 엑셀은 주최 측 자료라 저장소에 올리지 않았습니다(`data/`는 git 제외). 없으면 시연용 참가자만 들어갑니다.

### 데모 시드가 만드는 것
- 체험 계정 `demo1`~`demo5`: 1~3은 프로필 작성 완료(바로 신청), 4~5는 프로필부터
- 가상데이터 291명 적재 → 지난 회차를 날짜순으로 자동 매칭 → 참석 기록이 없어 전원 참석으로 종료
- 지난 목요일: `demo2`가 포함된 모임을 매칭 → 체크인 → 종료 → 일부 후기·신고까지 진행 (demo2는 후기를 직접 쓸 수 있게 남김)
- 다가오는 목요일 4회차: 회차마다 지역별 5명씩 결제 완료 대기 참가자 → 체험 계정이 신청하고 마감을 돌리면 테이블에 들어감

### 환경 변수

| 변수 | 기본값 | 설명 |
|---|---|---|
